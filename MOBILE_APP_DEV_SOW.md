## Outcome and boundaries

Deliver an installable **NER LENS Driver** Android app for assigned drivers, with field-observation functions shown only to accounts that also have the `field_reporter` role. It must complete the medicine-delivery journey with Control and Authority: assignment → acceptance → active trip → offline evidence and GPS recovery → authorized route-change alert → driver decision → delivery declaration → dispatcher confirmation. The app is responsible for device UX, local durability, permissions, and synchronization. The backend remains the authority for identity, jurisdiction, mission state, road status, route comparison, and audit.

Use React, TypeScript, and Capacitor as approved in the local project roadmap at `D:\SIH-2026\ROADMAP_v1.md`, with a native Android component where the device trial proves it is needed. Reuse behavior and validation from the Field PWA selectively; do not ship a WebView wrapper and call it reliable active-trip tracking. Use the supplied NER LENS SVG mark from [`public/icon.svg`](public/icon.svg) for the app identity, preserving Android adaptive-icon safe area. The shareable visual reference is [`design/logistics-network-control.html`](design/logistics-network-control.html); the local `D:\Tiny Scripts\Logistics-Demo frontend` is a further visual reference only. Do not integrate TinyScripts code or services. Keep any Jev/Gemini decision support on the backend, advisory, and separate from road authority.

This scope does **not** give the mobile client permission to publish a road closure, approve a route, calculate a supposedly truck-safe route, confirm final delivery on behalf of dispatch, or expose Mappls/GraphHopper keys. Push notifications supplement a persisted in-app inbox; they cannot be the only alert path.

## Screen and app routing contract

These are **proposed mobile screen paths**, not existing server endpoints. Deep links and Android Back must return to a safe signed-in screen, never a different account's cached trip.

| Screen route | Who may see it | Entry and exit behavior | API and offline behavior |
|---|---|---|---|
| `/login` | Signed out | Email/password, session expiry, explicit logout; do not retain a plaintext password. | Prove login → cookie/session → logout on a physical device before other feature work. |
| `/missions` | `driver` | Only currently assigned missions, state, deadline, sync age, and pending actions. | `GET /v1/corridors`, then `GET /v1/missions?corridor_id=…`; show an account-scoped cached summary offline. |
| `/missions/:id` | Assigned driver | Assignment, vehicle, destination/receiving facility, delivery window, state history; accept or reject while planned; start after acceptance; declare delivery only while active. | `GET /v1/missions/{id}` and the four lifecycle POSTs below. A queued action is visibly pending until acknowledged. |
| `/missions/:id/trip` | Assigned driver | Current saved planning baseline, age/expiry, route change awaiting decision, location sharing switch, and text/table alternative to the map. | `GET /v1/missions/{id}/route-selection` returns the selected candidate geometry and source provenance. Offline geometry is stale planning context, never navigation clearance. |
| `/missions/:id/report` | `field_reporter` only, including a dual-role driver | Geotagged observation, photo capture, review status, and clarification reply. | Durable local report/photo outbox; `POST /v1/field-reports` before media PUT. A driver-only account must not get this action until backend roles are changed or a second role is granted. |
| `/alerts` and `/alerts/:id` | Assigned driver | Persisted inbox; review cause, old/candidate route IDs and expiry; accept or decline once. | `GET /v1/alerts`, `POST /v1/alerts/{id}/acknowledge`; cached alerts and decisions survive restart. |
| `/sync` | Signed-in owner | Counts and reasons for saved, sending, acknowledged, reauth-required, conflict, and failed items; manual retry. | Replay only the original owner's queue, in dependency order. Do not delete uncertain writes. |
| `/settings` | Signed-in owner | Consent, location state, notification permission, storage age, language and logout. | Stop tracking on mission end, withdrawal of consent, logout, or role revocation; clear private trip views on account switch. |

The home screen must use plain status labels. “Unavailable” alone is not an adequate explanation: distinguish no assignment, offline cached, expired route, permission denied, provider outage, conflict, and session expiry. Every map view needs a readable route/segment list and uncertainty text.

## Network, authentication, and API routing

**First integration gate:** The current backend accepts an HTTP-only, `SameSite=Strict` session cookie from `POST /v1/auth/login`; hosted `/v1/*` requests also require the Cloudflare gateway's server-side secret. It also checks request origin and rejects cross-site mutation requests. The Capacitor WebView/native HTTP cookie and origin boundary has **not** been tested. Prove on an actual Android build that login, `Set-Cookie`, `GET /v1/auth/session`, one protected mission read, logout, and re-login work through the gateway without exposing a token or proxy secret to JavaScript logs, local storage, or the APK. If that fails, the backend owner must design and test a mobile session contract before feature implementation continues. Capacitor's native HTTP client exists, but cookie behavior and larger binary uploads require an app-specific spike; its documentation notes special handling for large files. [Capacitor HTTP](https://capacitorjs.com/docs/apis/http).

Use the committed [OpenAPI snapshot](https://github.com/yash7124ja-bit/NER_LENS/blob/main/docs/openapi/v1.json) as the exact request schema. The table below is the screen-to-API map, not a substitute for generated types or server validation. Mutations with `Idempotency-Key` must save a stable UUID with the local action and reuse it on every retry; never generate a new key after a timeout.

| Mobile flow | Existing API | Request and server result that matter |
|---|---|---|
| Session | `POST /v1/auth/login`, `GET /v1/auth/session`, `POST /v1/auth/logout` | JSON login `{email,password}`; keep the server session in a protected cookie container; 401/403/429 must be distinct UI states. |
| Assigned missions | `GET /v1/missions?corridor_id=…`, `GET /v1/missions/{mission_id}` | Server filters driver assignment and jurisdiction. Detail includes state, assigned vehicle/driver, deadline, last-fix age, and authorized receiving contact. |
| Lifecycle | `POST /v1/missions/{id}/accept`, `/reject`, `/start`, `/declare-delivery` | Empty body plus `Idempotency-Key`. Server enforces `planned → accepted → active → delivered`; the owning dispatcher separately calls `/confirm-delivery`. A 409 must stop dependent queued actions. |
| GPS batch | `POST /v1/missions/{id}/positions` | Body `{device_id,sequence_start,points}`. Each point has unique `sequence`, UTC `captured_at`, GeoJSON `Point` `[longitude,latitude]`, `accuracy_m`, optional `speed_mps`/`heading_deg`; maximum 500 points/request. Inspect `accepted`, `duplicate`, `rejected`, and `flagged` receipts before deleting local points. |
| Current route metadata | `GET /v1/missions/{id}/route-selection` | Returns selected `route_id`/`comparison_id`, saved candidate geometry/metrics, source provenance, selection time, expiry, and `planning_baseline_only` or `expired_baseline`. It is still an unverified planning baseline, not a full navigation trip. |
| Route-change inbox | `GET /v1/alerts`, `POST /v1/alerts/{id}/acknowledge` | Acknowledgment body `{decision:"accept"|"decline"}` plus stable key. Accept triggers a fresh server check and may change selection; decline leaves it unchanged. A first inbox read records an in-app delivery attempt separately from acknowledgment. |
| Observation | `POST /v1/field-reports`, `GET /v1/field-reports/{id}/history`, `POST /v1/field-reports/{id}/clarifications` | Reporter role and ownership required. Report includes stable `client_report_id`, sequence, observed time, segment, coordinates, accuracy, claim, condition, note and device ID. Never convert a report claim into road status locally. |
| Photo | `PUT /v1/field-reports/{id}/media/{slot}`, `GET /v1/field-reports/{id}/media` | Four slots `0..3`; JPEG/PNG/WebP, at most 8 MiB each; send `Idempotency-Key`, `X-Media-SHA256`, content type/length and raw bytes. Upload may return 503 until private storage and ClamAV are configured; keep bytes and show retry. Only cleared derivatives may be displayed. |
| Read-only corridor context | `GET /v1/corridors`, `/v1/corridors/{id}/state`, `/v1/corridors/{id}/map-route`, `GET /v1/maps/config` | The map-route response is provider context, not a turn-by-turn or verified truck route. `offline_tiles` is currently false. Always show source age and status uncertainty. |

The mobile client must **not** call dispatcher-only `POST /v1/routes/compare`, route-selection POST, route-change-approval POST, status publication, or mission confirmation. These are Control/Authority responsibilities. Backend tests already cover wrong role/jurisdiction, revoked assignment, invalid transitions and repeat keys; the mobile client must still prove the device behavior.

## Road routing and disruption behavior

1. **Before departure:** Control creates the mission, compares candidates, and saves one expiring *planning baseline*. The driver reads it; the app does not choose a route. The comparison currently uses a car free-flow baseline and labels vehicle entitlement, road graph, restrictions, ETA uncertainty, and source quality as unverified. `recommended_route_id` is deliberately `null`. Display this warning next to every route, including offline copies.
2. **Trip read:** `GET /v1/missions/{id}/route-selection` now gives the assigned driver the persisted selected candidate and source provenance, including geometry, graph version, snapshot ID, and retrieval time. Backend owner still needs a complete versioned trip contract before native navigation: mission/assignee, verified vehicle constraints, decision IDs, effective status/freshness, human-readable limitations, and server time. The client must not treat the current planning baseline as truck-safe or call Mappls directly.
3. **During a restriction:** Authority publishes an expiring decision. Backend computes candidate mission impacts; Control compares and approves an alternative. Backend creates one assigned-driver alert. The mobile app presents **current route** and **pending candidate** separately, with cause, expiry, confidence/limitations, and dispatcher reason. It must never silently switch. `accept` sends the alert acknowledgment and adopts the new saved selection only after server confirmation; `decline` leaves the current selection unchanged and tells Control. On 409 (expired alert, changed graph/decision/source, unverified candidate), show “route needs reassessment” and refresh; do not retry forever.
4. **No feasible route or outage:** Show a stop-and-contact-dispatch state with the last known route clearly marked stale. A provider timeout or missing basemap is not evidence that a road is open. GPS is a position record, not proof of legal or safe passability.
5. **Future road-valid navigation gate:** A backend/geo owner must verify a versioned road-edge graph, Mappls heavy-vehicle entitlement and actual restrictions, vehicle dimensions/weight, direction/closure rules, and an approved route policy before “truck-safe” or turn-by-turn instructions are enabled. Mappls explicitly requires enabled account access for its heavy-vehicle API. [Mappls heavy-vehicle routing](https://developer.mappls.com/mapping/routing-for-heavy-vehicles/). Until that evidence exists, the mobile screen is a route **review** with a text alternative, not a navigation product.

## Offline, native device, and data rules

- Use an encrypted, account-scoped local store for mission summaries, alert snapshots, queued mutations, GPS points, report drafts, and photo file references. Keep the original owner, mission ID, dependency order, idempotency key, capture time, retry count, and expiry with each item. A logout/account switch hides and clears the prior user's readable trip cache; it must not submit that user's pending work as another account. Do not log credentials, contact details, raw media, or position tracks.
- On reconnect, verify session/role/assignment first. Replay each dependency chain in order: mission acceptance before start, confirmed start before GPS, canonical report before its media; alert acknowledgment is an independent, time-sensitive chain and must not wait behind photo uploads. Preserve bytes and keys across timeout, app restart, screen lock and process death. A 401 pauses for reauthentication; 403/revocation or 409 conflict pauses the affected chain and asks for review; 429/502/503 retry with backoff. Render's free-tier wakeup is not an excuse to drop a queue.
- Ask for location permission in context. Start mission-bound sharing only after consent and active-trip state; show an obvious stop control and persistent sharing indicator. Support approximate/denied permission with an explicit reduced-function mode. For screen-off tracking, evaluate a native `location` foreground service started while the app is visible, with required permission/notification behavior on the intended Android versions. Capacitor's standard Geolocation plugin does **not** directly supply background geolocation. [Capacitor Geolocation](https://capacitorjs.com/docs/apis/geolocation), [Android location permissions](https://developer.android.com/develop/sensors-and-location/location/permissions), [foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types). Do not request all-time background location unless a documented trip requirement and device trial justify it.
- Keep the in-app alert inbox working when notification permission is denied or push is unavailable. There is currently no device-token registration/push-dispatch API. If push is added, backend owner must define registration, revocation, recipient scope, and delivery receipts; Android notification permission must be tested on supported OS versions. [Capacitor Push Notifications](https://capacitorjs.com/docs/apis/push-notifications).
- Native photo capture must preserve original bytes/checksum through upload retry; never expose pending, rejected, or scanner-error raw media. Current hosted private storage/scanner clearance is an external dependency, so the app must show “saved locally / awaiting secure upload” rather than claim submission complete.
